# Продажи: обогащение

## Что делает

Добирает по каждой выжившей компании три вещи:

1. **сайт** и с него **почту**
2. **ФИО директора** из ЕГРЮЛ
3. **техническое состояние сайта**, которое дальше станет поводом для письма

Главный принцип: **каждый факт записывается вместе с источником и уверенностью**. Письмо строится на фактах, и если факт добыт слабым способом, это должно быть видно человеку до отправки, а не после.

## Когда вызывать

- после `/продажи отсев`, по тем, кто не попал в таблицу `otsev`
- когда нужно обновить контакты по уже собранной базе
- когда человек просит добрать директоров отдельно

**Не запускай обогащение на всей исходной выборке.** Это дорого по времени и не нужно: смысл отсева в том, чтобы сюда пришли только выжившие.

## Модель фактов

Результат ложится в таблицу **`enrichment`** базы `data/leads.db`:

| Колонка | Что |
|---|---|
| `inn` | ключ, связь с `companies` |
| `name` | название, чтобы отчёт читался без джойна |
| `website` | найденный сайт |
| `email` | найденная почта |
| `director` | должность и ФИО руководителя |
| `revenue` | выручка, тыс. руб., если уточнялась здесь |
| `source` | откуда взято: `egrul`, `rmsp`, `site:/contacts/`, `site:footer`, `gir-bo` |
| `confidence` | `high`, `medium`, `low` |
| `checked_at` | когда добыто |

**Одна строка на один ИНН.** Отчёт считает `количество строк` как «компаний обогащено», поэтому несколько строк на одну компанию сломают статистику.

Отсюда следствие: у одной строки один `source` и один `confidence`, а фактов в ней три. Правило разрешения:

- в `confidence` пиши **худшую** уверенность среди заполненных полей. Так низкое качество не спрячется за высоким
- в `source` перечисли источники коротко через запятую: `egrul, site:/contacts/`
- **пофактовую расшифровку** сохраняй в дополнительной колонке `facts_json` (источник и уверенность по каждому полю отдельно). `report.py` про неё не знает и спокойно игнорирует, а `/продажи письмо` читает её, чтобы решить, какой факт можно ставить в текст

Так требование «каждый факт с источником и уверенностью» выполняется, и отчёт при этом остаётся правильным.

### Шкала уверенности, применяй её механически

| Уровень | Когда ставить |
|---|---|
| **high** | факт получен из ЕГРЮЛ или реестра МСП по **точному совпадению ИНН**. Сюда же почта, найденная на странице `/contacts/` домена, чей ИНН со страницы реквизитов совпал с ИНН компании |
| **medium** | сайт найден поиском по названию и совпал по городу либо по фрагменту названия, но ИНН на сайте не подтверждён. Почта с домена этого сайта |
| **low** | сайт найден только по названию, подтверждения нет. Почта общего вида `info@` без подтверждения принадлежности. Любое сопоставление по названию без ИНН |

**Факты уровня `low` не попадают в письмо как утверждения.** Либо перепроверяются, либо компания идёт в письмо без этого факта.

## Пошаговый алгоритм

### Шаг 1. Собери рабочий список

Возьми выживших после отсева:

```sql
SELECT * FROM companies WHERE inn NOT IN (SELECT inn FROM otsev);
```

Покажи человеку число и **оценку времени**: примерно 2 секунды на запрос в ЕГРЮЛ плюс несколько секунд на сайт. На 400 компаний это десятки минут в один поток, поэтому дальше параллелим.

### Шаг 2. Сверь сигнатуры скриптов

Оба скрипта разбирают аргументы через argparse, поэтому `--help` безопасен: справка печатается без единого запроса в сеть. У `fns_egrul.py` живая часть спрятана за ключом `--live`, без него он только показывает план прогона.

```bash
PRODAZHI="$HOME/.claude/tools/prodazhi"; [ -d "$PRODAZHI/scripts" ] || PRODAZHI="$(pwd)"
python3 "$PRODAZHI/scripts/fns_egrul.py" --help
python3 "$PRODAZHI/scripts/enrich_site.py" --help
```

Рабочие вызовы:

```bash
PRODAZHI="$HOME/.claude/tools/prodazhi"; [ -d "$PRODAZHI/scripts" ] || PRODAZHI="$(pwd)"
python3 "$PRODAZHI/scripts/fns_egrul.py"  --db data/leads.db --inn-file /tmp/chunk_01.txt --live
python3 "$PRODAZHI/scripts/enrich_site.py" --db data/leads.db --inn-file /tmp/chunk_01.txt
```

`fns_egrul.py` кладёт ФИО руководителя в колонку `director` таблиц `companies` и `enrichment`, и **именно из неё письмо берёт обращение по имени**. Без списка ИНН он сам возьмёт из базы тех, у кого ФИО ещё нет. `enrich_site.py` спрашивает ЕГРЮЛ сам, если ФИО в базе ещё нет; отключается ключом `--no-director`.

Если флаги отличаются, следуй скрипту, а не этому файлу.

### Шаг 3. Параллелизация через субагентов Task

Разбей список на куски и запусти субагентов **одним блоком вызовов**, а не по очереди.

Правила параллелизации:

- **по сайтам**: 4-6 субагентов, у каждого свой кусок ИНН. Сайты это разные хосты, они друг другу не мешают
- **по ЕГРЮЛ: максимум 2 субагента.** Это один хост ФНС, и разгонять его нельзя. Замерено: 25 запросов подряд с паузой 0.3 секунды прошли без капчи, темп примерно 1 запрос в 2 секунды получается сам собой. Не пытайся ускорить
- каждый субагент пишет **в свой временный файл**, а не напрямую в sqlite. Sqlite плохо переносит параллельную запись. Слей результаты в базу сам, одним проходом, после того как все субагенты вернулись
- задание субагенту формулируй узко: вот список ИНН, вот скрипт, верни путь к файлу результата и число обработанных. Не давай субагенту свободы менять логику

### Шаг 4. ЕГРЮЛ, ФИО директора

Единственный источник ФИО руководителя. Капчи нет.

Схема двухшаговая, обе фазы обязательны:

```
POST https://egrul.nalog.ru/
     query=<ИНН>&region=&page=&vyp3CaptchaToken=&PreventChromeAutocomplete=
→ {"t":"<токен>","captchaRequired":false}

GET  https://egrul.nalog.ru/search-result/<токен>
→ {"rows":[...]}
```

Второй запрос **иногда отдаёт пустой ответ, пока поиск ещё идёт**. Опрашивай с интервалом около 0.5 секунды, пока не появится `rows`. Не считай первый пустой ответ ошибкой.

Ищи **строго по ИНН**. Поиск по ИНН даёт точное попадание, `tot=1`. Поиск по названию нечёткий и полнотекстовый: запрос «Кайбицкий хлебокомбинат» даёт **1327** результатов. Названием идентифицировать компанию нельзя.

Поля ответа:

| Поле | Что |
|---|---|
| `g` | **должность и ФИО руководителя**, формат `ДОЛЖНОСТЬ: Фамилия Имя Отчество`. Может содержать несколько лиц через запятую |
| `n` | полное наименование юрлица либо ФИО предпринимателя |
| `c` | краткое наименование |
| `i`, `o`, `p` | ИНН, ОГРН, КПП |
| `r` | **дата регистрации**, здесь она точная, в отличие от даты включения в реестр МСП |
| `e` | дата прекращения деятельности, есть **только у ликвидированных**. Если поле пришло, компанию надо вернуть в отсев |
| `k` | `ul` юрлицо, `fl` предприниматель |

**Важно про ИП.** У записей с `k = "fl"` полей `c`, `p` и **`g` нет вообще**. ФИО предпринимателя лежит в `n`. Не считай отсутствие `g` ошибкой, это нормально для ИП. Уверенность по такому ФИО всё равно `high`, источник тот же ЕГРЮЛ.

Разбирай `g` на должность и ФИО по первому двоеточию. Если лиц несколько, бери первое, а остальных сложи в `facts_json`.

### Шаг 5. Сайт

**Ключевое разделение труда, без него сайты не находятся.** Скрипт `enrich_site.py` НЕ умеет искать в поисковиках: DDG, Яндекс, Brave блокируют скрипты капчами (замер 13.08.2026). Скрипт умеет только два слабых пути: колонка WWW реестра (обычно пустая) и угадывание домена по транслиту названия. **Поэтому сайты ищешь ТЫ, агент, своим веб-поиском** — тебе капча не мешает, ты ищешь как человек.

Процедура на каждую компанию без сайта (проверена живьём 15.08.2026):

1. Веб-поиск: `<короткое название> <город> официальный сайт` (название без ООО/АО и кавычек).
2. В выдаче отфильтруй справочники — это НЕ сайты компании: rusprofile, zachestnyibiznes, spark-interfax, sbis/saby, list-org, companium, vbankcenter, 2gis, orgpage. Кандидат — только собственный домен компании.
3. Кандидата проверь по ИНН: скачай главную и страницы `/kontakty`, `/contacts`, `/rekvizity`, `/about`, политику — ищи ИНН компании простым поиском по тексту. Нашёл и совпал → `high`.
4. ИНН не нашёлся, но название и город совпадают → `medium`.
5. В выдаче только справочники → **у компании нет сайта, это нормальный результат**, не ошибка. Пометь в `facts_json` «сайт не найден поиском», компания идёт дальше без сигналов сайта.

Побочная ценность выдачи: сниппеты справочников часто показывают телефон и почту. Забирай их в `facts_json` с уверенностью `low` — в письмо они не попадут, но человеку пригодятся. Сами страницы справочников не парсить: капчи и запрет в правилах.

Порядок поиска сайта целиком, от надёжного к слабому:

1. колонка `website` таблицы `companies`, пришла из реестра МСП. Заполняется добровольно и **обычно пустая**, но если есть, это уверенность `high`
2. твой веб-поиск по процедуре выше
3. угадывание домена скриптом по транслиту названия — оставь скрипту, иногда попадает (chelny-hleb.ru)

**Подтверждение сайта по ИНН это главный приём.** Если на сайте нашёлся ИНН и он совпал с ИНН компании, уверенность поднимается до `high`. Регулярка проверена живьём:

```
ИНН\D{0,10}(\d{10}|\d{12})
ОГРН\D{0,10}(\d{13}|\d{15})
```

Честная оговорка по эффективности: на тестовом корпусе из 7 крупных сайтов ИНН нашёлся **только на одном**. У малого бизнеса реквизиты в футере встречаются чаще, но цифру подтвердить нечем. Значит большая часть сайтов останется на уверенности `medium`, и это нормально.

### Шаг 6. Почта

**Почту эффективнее брать со страницы `/contacts/`, а не со страницы политики.** Это прямой результат проверки: email нашёлся на 5 сайтах из 7, и почти всегда именно на контактах.

Перебирай пути: `/contacts/`, `/kontakty/`, `/contact/`, затем главную, затем `/policy/`, `/politika-konfidencialnosti/`, `/privacy/`, `/rekvizity/`.

Регулярка почты, проверена живьём:

```
[a-zA-Z0-9._%+-]+@[a-zA-Z0-9.-]+\.(?:ru|com|рф|net|org|su)\b
```

Приоритет при выборе одной почты из нескольких: адрес на **домене самой компании** выше, чем на публичном почтовике. `info@`, `sales@`, `zakaz@` выше, чем личная почта сотрудника. Почту вида `noreply@`, `webmaster@` и адреса разработчиков сайта отбрасывай.

Страница политики нужна ровно для одного: достать **ИНН** и подтвердить, что сайт принадлежит этой компании.

### Шаг 7. Читай HTML целиком

**Это обязательное правило, а не оптимизация.** В первом прогоне разведки чтение обрезали на 500 КБ и потеряли футеры. Реальные размеры живых страниц: `segezha-group.com` **1 324 133** байта, `kzsk.ru` **769 115** байт. Копирайт, ИНН и почта живут именно в футере. Обрезка даёт ложный вывод «у них нет реквизитов».

### Шаг 8. Технические признаки состояния сайта

Снимай их тем же запросом, второй раз ходить не надо. Все регулярки проверены на живом корпусе:

| Признак | Регулярка | Попаданий на корпусе |
|---|---|---|
| Яндекс.Метрика | `mc\.yandex\.ru/(?:metrika\|watch)\|ym\s*\(\s*\d{5,9}\s*,` | 5 из 7 |
| Номер счётчика | `(?:ym\s*\(\s*\|mc\.yandex\.ru/watch/)(\d{5,9})` | 5 из 7 |
| Адаптив | `<meta[^>]+name\s*=\s*["']viewport["']` | 7 из 7 |
| Форма на странице | `<form\b[^>]*>` | 5 из 7 |
| Телефон | `(?:\+7\|\b8)[\s\-(]*\d{3}[\s\-)]*\d{3}[\s\-]*\d{2}[\s\-]*\d{2}` | 6 из 7 |
| Год в копирайте | `(?:©\|&copy;\|&#169;)\s*(?:\d{4}\s*[–—−-]\s*)?(20\d{2})` | 4 из 7 |
| CMS Битрикс | `/bitrix/(?:js\|templates\|cache)/` | 5 из 7 |

Плюс замеры, которые снимаются самим запросом: **SSL**, **время до ответа**, **код ответа**, **размер страницы**. Живые значения времени ответа с корпуса: 1.50, 1.59, 1.75, 1.97, 2.15, 2.59, 3.20 секунды.

Два важных предупреждения:

**Проверяй отсутствие Яндекс.Метрики, а не отсутствие Google Analytics.** GA не нашёлся **ни на одном** из 7 производственных сайтов, и это не сбой регулярки: после ухода Google рынок переехал на Метрику. «Нет GA» в России сегодня не боль, а норма, и письмо на этом строить нельзя.

**Виджеты чатов и форм часто вставляются джаваскриптом после загрузки.** На сайтах, собранных на Next.js, их в сыром HTML **нет вообще**. Значит регулярка по сырому HTML систематически недосчитывает чаты. Вывод «у них нет онлайн-чата» на основании сырого HTML делать **нельзя**, надёжно это ловится только headless-браузером.

### Шаг 9. PageSpeed, только если у человека есть ключ

**Без ключа PageSpeed Insights не работает.** Проверено 6 раз подряд по 6 разным доменам, во всех случаях **HTTP 429**: общий анонимный пул Google исчерпан посторонними людьми, повлиять на это нельзя. Документация Google прямо пишет, что ключ нужен для автоматических запросов.

Спроси у человека, есть ли ключ. Если нет, **не обещай PageSpeed** и используй собственные замеры из шага 8, они работают всегда и откуда угодно.

### Шаг 10. Не ходи в pb.nalog.ru

Соблазн есть: он отдаёт готовый `bourl` и статус одним запросом. Но порог капчи там плавающий и накопительный, привязан к **IP**, а не к куке: в замерах она включалась и на 4-м поиске, и на 14-м, и держится **больше 30 минут**. Новая сессия с чистыми куками счётчик не обнуляет, это проверено явно. Для массового обогащения он непригоден.

### Шаг 11. Слей результаты и построй отчёт

Слей временные файлы субагентов в `data/leads.db` одним проходом. Посчитай покрытие по каждому полю.

**HTML руками не пиши**, отчёт собирает `scripts/report.py` из таблицы `enrichment`.

```bash
PRODAZHI="$HOME/.claude/tools/prodazhi"; [ -d "$PRODAZHI/scripts" ] || PRODAZHI="$(pwd)"
python3 "$PRODAZHI/scripts/report.py" --db data/leads.db --out out --only obogashchenie
open out/obogashchenie.html
```

Это **отчёт шага 3 из 5**. Генератор сам выведет плашки покрытия (сколько нашли сайт, почту, ФИО), разбивку по `source` и **колонку источника** в таблице, а строки с низкой уверенностью подсветит и посчитает отдельной плашкой. Именно поэтому важно честно проставлять `confidence`: подсветка ненадёжного работает только на честных данных.

Пофактовую расшифровку из `facts_json` в отчёт покажи **сам, в чате**, по компаниям с `confidence = low`. Это то, что человеку нужно проверить глазами до письма.

## Какие скрипты запускает

| Скрипт | Роль |
|---|---|
| `scripts/fns_egrul.py` | ФИО директора, дата регистрации, признак ликвидации по ИНН |
| `scripts/enrich_site.py` | поиск сайта, почта, ИНН со страницы, технические признаки |

## Что показывает человеку

- сколько компаний обогащается и **оценку времени до старта**, а не после
- прогресс по мере возврата субагентов
- покрытие по каждому полю в процентах
- **отдельный список фактов с уверенностью `low`**, которые не пойдут в письмо без проверки
- честно: если ключа PageSpeed нет, скорость сайта меряется собственным замером времени ответа
- ссылку на `out/obogashchenie.html`
- следующий шаг: `/продажи сигналы` либо сразу `/продажи письмо`

## Возможные ошибки и что делать

| Симптом | Причина | Что делать |
|---|---|---|
| ЕГРЮЛ вернул пустой ответ | поиск ещё идёт на сервере | опрашивай `search-result/<токен>` каждые 0.5 секунды. Это норма, не ошибка |
| У компании нет поля `g` | это ИП, `k = "fl"` | у ИП полей `c`, `p`, `g` нет. ФИО лежит в `n` |
| Пришло поле `e` | компания **ликвидирована** | верни её в отсев, не пиши ей письмо |
