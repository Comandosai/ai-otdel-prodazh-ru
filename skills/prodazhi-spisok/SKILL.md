# Продажи: сбор списка

## Что делает

Забирает **всю нишу целиком одним файлом** из Единого реестра субъектов МСП и кладёт в локальную базу. Это ядро конвейера: отсюда берут данные все следующие шаги.

Один POST на `rmsp.nalog.ru/report.xlsx` отдаёт 5084 строки за **2.0 секунды**. Ни капчи, ни ключа, ни авторизации. Замер живой, 13.08.2026.

## Когда вызывать

- утверждён портрет в `config.json` и нужен список компаний
- человек просит пересобрать выборку после правки портрета
- нужен свежий срез для сравнения с вчерашним (это же нужно `/продажи сигналы`)

## Чего делать нельзя

**Не используй `pb.nalog.ru` для массовой выборки.** Замерено: порог капчи плавающий и накопительный, привязан к IP, а не к сессии. Капча включалась и на 4-м поиске, и на 14-м, держится **больше 30 минут**, новые куки счётчик не обнуляют. Считай по нижней границе, по 3-4 поискам. Если запустишь массовый сбор через pb, ты сожжёшь IP человеку на полчаса прямо посреди работы.

Единственный безопасный источник массового списка это **`rmsp.nalog.ru/report.xlsx`**.

## Пошаговый алгоритм

### Шаг 1. Проверь вход

Конфиг в конвейере один: **`config.json`**. Отдельного `config/icp.json` нет. Путь вычисляй, а не пиши руками: скрипты и конфиг ставятся в `~/.claude/tools/prodazhi/`, а рабочая папка человека может быть любой.

```bash
PRODAZHI="$HOME/.claude/tools/prodazhi"; [ -d "$PRODAZHI/scripts" ] || PRODAZHI="$(pwd)"
cat "$PRODAZHI/config.json"
```

Читаешь блоки `portret_klienta` (регион, коды ОКВЭД, тип субъекта, категория МСП) и `vilki` (численность, выручка). Если блока `portret_klienta` нет или он пуст, **не выдумывай фильтры**, скажи человеку запустить `/продажи портрет` и остановись.

Проверь, что в конфиге есть хотя бы регион и хотя бы один код ОКВЭД.

### Шаг 2. Проверь интерфейс скрипта

`scripts/fns_rmsp.py` разбирает аргументы через argparse, поэтому `--help` безопасен: он печатает справку и выходит, **в сеть не идёт и файлов не создаёт**. Живая часть спрятана за ключом `--live`: без него скрипт только показывает параметры выборки и останавливается.

```bash
PRODAZHI="$HOME/.claude/tools/prodazhi"; [ -d "$PRODAZHI/scripts" ] || PRODAZHI="$(pwd)"
python3 "$PRODAZHI/scripts/fns_rmsp.py" --help
```

Рабочий вызов:

```bash
PRODAZHI="$HOME/.claude/tools/prodazhi"; [ -d "$PRODAZHI/scripts" ] || PRODAZHI="$(pwd)"
python3 "$PRODAZHI/scripts/fns_rmsp.py" --config "$PRODAZHI/config.json" --db data/leads.db --live
```

Полезные ключи: `--region 16`, `--okved 10.71,10.51`, `--limit 500`, `--employees-from 15`, `--employees-to 400`, `--exclude-okved 49.41`, `--xlsx путь` (с `--live` выгрузка сохраняется туда, с `--offline` читается оттуда без сети). Значения из ключей перебивают конфиг, а если конфига по указанному пути нет, скрипт найдёт `config.json` сам и скажет об этом.

Если флаги отличаются, **следуй скрипту, а не этому файлу**. Скрипт это источник правды по своему интерфейсу.

### Шаг 3. Запусти сбор

Скрипт внутри делает ровно это, и тебе полезно понимать логику, чтобы разбирать ошибки:

1. `GET https://rmsp.nalog.ru/search.html?mode=extended` чтобы забрать куки. **Без этого шага дальше будет отказ.**
2. `POST https://rmsp.nalog.ru/report.xlsx` с формой:

| Параметр | Значение | Комментарий |
|---|---|---|
| `mode` | `extended` | обязательный |
| `npType` | `UL` | юрлица. `IP` отдельным прогоном, если нужно |
| `dtCategory` | `10.08.2026` | **обязательный**, всегда **10-е число месяца** |
| `region` | `16` | код ФНС из конфига |
| `okved1` | `10.71` | можно списком через запятую |
| `sortField` | `NAME_EX` | |
| `sort` | `ASC` | |

3. Читает xlsx встроенным парсером на `zipfile` и `ElementTree`, `openpyxl` подключается только как запасной путь.
4. Применяет бесплатный отсев (численность, ОКВЭД, исключённые из реестра) и кладёт результат в `companies` через `verify.db_upsert_company`.

### Шаг 4. Что приходит в 22 колонках

Реестр отдаёт больше, чем ожидаешь от бесплатного источника:

| Колонка xlsx | Поле в базе | Ценность для конвейера |
|---|---|---|
| ИНН | `inn` | **первичный ключ всего конвейера** |
| ОГРН | `ogrn` | |
| Наименование / ФИО | `name` | |
| Основной вид деятельности | `okved`, `okved_name` | база для отсева по своему ОКВЭД |
| Регион, Район, Город, Населенный пункт | `region`, `area`, `city` | |
| Категория | `category` | 1 микро, 2 малое, 3 среднее |
| **Среднесписочная численность** | `employees` | **фильтр по размеру бесплатно** |
| Вновь созданный | `is_new` | повод для письма |
| Дата включения в реестр | `dt_registry` | |
| Дата исключения из реестра | `dt_registry_out` | заполнено только у выбывших |
| Наличие лицензий | `has_licenses` | |
| Телефон, E-mail, WWW | `phone`, `email`, `website` | **часто пустые**, заполняются добровольно |

Признак **госконтрактов** (`has_contracts`) приходит в JSON-выдаче `search-proc.json`, и это бесплатная замена недоступному ЕИС. В колонках xlsx его нет. Если скрипт умеет добирать его отдельным проходом, включи, но **не считай его обязательным** для этого шага.

### Шаг 5. Схема базы, общий контракт всего конвейера

База одна: **`data/leads.db`**. Это же значение стоит по умолчанию в `scripts/report.py`, не меняй его без причины. Файл `out/demo.db` это артефакт демо-режима, рабочие данные туда не пиши.

Пять таблиц, каждую наполняет свой шаг конвейера:

| Таблица | Кто пишет | Колонки |
|---|---|---|
| **`companies`** | этот скилл, дополняет `/продажи отсев` | `inn`, `ogrn`, `name`, `okved`, `okved_name`, `region`, `area`, `city`, `category`, `employees`, `has_contracts`, `has_licenses`, `is_new`, `dt_registry`, `phone`, `email`, `website`, `collected_at`, **`revenue`**, **`status`**, **`status_date`**, **`address`** |
| `otsev` | `/продажи отсев` | `inn`, `name`, `reason`, `rule`, `dropped_at` |
| `enrichment` | `/продажи обогащение` | `inn`, `name`, `website`, `email`, `director`, `revenue`, `source`, `confidence`, `checked_at` |
| `signals` | `/продажи сигналы` | `inn`, `name`, `signal`, `detail`, `severity`, `source`, `checked_at` |
| `letters` | `/продажи письмо` | `inn`, `name`, `to_email`, `subject`, `body`, `facts`, `status`, `created_at` |

**Держись этих имён при записи.** `scripts/report.py` умеет распознавать синонимы колонок, но канонические имена читаются однозначно и не зависят от таблицы синонимов.

Последние четыре колонки `companies` (`revenue`, `status`, `status_date`, `address`) на этом шаге остаются пустыми: их заполняет `/продажи отсев`, когда добирает выручку из ГИР БО. Таблицу и недостающие колонки создаёт сам скрипт (`verify.open_db` плюс `verify.ensure_company_columns`), руками схему писать не нужно.

На этом шаге ты наполняешь только **`companies`**. Численность из реестра (`od2_sschr`) ложится в колонку **`employees`**. Колонки `phone`, `email`, `website` заполняются из добровольных колонок xlsx и **обычно пустые**, настоящие контакты добудет обогащение.

Запись идёт по `inn`: `verify.db_upsert_company` обновляет существующую строку и не затирает пустотой то, что уже собрали другие шаги. Повторный прогон дублей не плодит, это проверяется счётчиком «всего уникальных компаний в базе» в выводе скрипта.

Дополнительно клади срез в таблицу **`snapshots`** (`dt_srez`, `inn`, `okved`, `employees`, `has_contracts`, `is_new`). Она нужна только `/продажи сигналы`, чтобы считать разницу между днями. `report.py` про неё не знает и спокойно её игнорирует. Не чисти её.

### Шаг 6. Посчитай разбивку

После загрузки посчитай прямо запросами к базе:

- всего компаний
- разбивка по `okved` с расшифровкой, по убыванию
- разбивка по `city`, топ 10
- сколько с заполненной численностью, медиана
- сколько с непустым `website` или `email`
- сколько с `is_new = 1`

### Шаг 7. Собери отчёт

**HTML руками не пиши.** В репозитории есть готовый генератор `scripts/report.py`, он читает базу и собирает все пять отчётов конвейера в едином оформлении.

```bash
PRODAZHI="$HOME/.claude/tools/prodazhi"; [ -d "$PRODAZHI/scripts" ] || PRODAZHI="$(pwd)"
python3 "$PRODAZHI/scripts/report.py" --db data/leads.db --out out --only sobrano
open out/sobrano.html
```

Это **отчёт шага 1 из 5**. Генератор сам посчитает плашки, разбивку по ОКВЭД и городам и таблицу компаний, если таблица `companies` заполнена канонически.

Если отчёт вышел пустым или с плашкой «таблица не создана», значит запись в базу не прошла. Иди проверять шаг 5, а не правь HTML.

## Какие скрипты запускает

| Скрипт | Роль |
|---|---|
| `scripts/fns_rmsp.py` | POST на `report.xlsx`, разбор xlsx, запись в sqlite |

Зависимость: **`openpyxl`** для чтения xlsx, она в `requirements.txt`. Всё остальное стандартная библиотека Python 3.9.

## Что показывает человеку

- сколько компаний нашлось, крупным числом
- разбивка по ОКВЭД и по городам
- сколько времени заняла выгрузка
- честное предупреждение: колонки Телефон, E-mail, WWW в реестре **обычно пустые**, контакты будем добывать на шаге обогащения
- ссылку на `out/sobrano.html`
- следующий шаг: `/продажи отсев`

## Возможные ошибки и что делать

| Симптом | Причина | Что делать |
|---|---|---|
| Пришло 0 записей | в конфиге класс ОКВЭД (`10`) вместо полного кода (`10.71`) | подтверждены живыми запросами только полные коды. Разверни класс в список полных кодов и повтори |
| Пришло 0 записей, коды полные | не передан `dtCategory` либо дата не 10-е число | `dtCategory` **обязательный**, формат `10.08.2026`, всегда 10-е число месяца |
| Ответ 403 или пустой | не забраны куки | сначала `GET https://rmsp.nalog.ru/search.html?mode=extended`, только потом POST |
| Возвращается ровно 10 записей | ушёл запрос на `search-proc.json`, а не на `report.xlsx` | `pageSize` сервером **игнорируется**, в JSON всегда 10. Массовая выгрузка только через `report.xlsx` |
| Пришла только первая страница | попытка листать `page=2` числом | `page` принимает **только подписанный токен** из `pageNav`. Не листай, бери xlsx |
| Фильтр по категории МСП не сработал | серверный `category` в замерах игнорировался | фильтруй категорию **локально** по колонке `category` уже в базе |
| Ответ не xlsx, а HTML | сессия протухла или сменилась форма | перезабери куки и повтори один раз. Если снова HTML, покажи человеку первые строки ответа, не притворяйся, что данные есть |
| Выборка больше 50 тысяч строк | верхний предел `report.xlsx` **не проверялся** разведкой, максимум замеренного 5084 строки | предупреди человека честно, дроби запрос по ОКВЭД или по районам |
| Хочется добрать данных через pb.nalog.ru | соблазн получить `bourl` и статус | **не делай этого массово**. Капча по IP, больше 30 минут, куки не спасают |

## Ограничение по свежести

Реестр МСП обновляется **10-го числа каждого месяца**. Значит `is_new` и `dt_registry` дают дискретность **месяц, а не день**. Для еженедельного конвейера этого достаточно, для ежедневного нужен дифф срезов, его делает `/продажи сигналы`.
