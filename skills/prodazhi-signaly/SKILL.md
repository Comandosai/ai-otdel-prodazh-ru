# Продажи: свежие поводы

## Что делает

Ищет **причину написать именно сейчас**. Письмо без повода это спам, письмо с поводом это деловое сообщение. Разница не в тексте, а в том, есть ли у тебя факт, объясняющий, почему письмо пришло сегодня.

Скилл собирает поводы шести типов и раскладывает их по компаниям из базы.

## Когда вызывать

- перед `/продажи письмо`, чтобы у писем был повод
- на регулярной основе, если конвейер работает еженедельно
- когда человек спрашивает, кто появился в нише за последнее время

## Шесть источников поводов, все бесплатные

### Повод 1. Новые в реестре МСП

Поле `is_new` из выборки. Признак «вновь созданный субъект» в смысле 209-ФЗ, то есть зарегистрирован в текущем календарном году.

Живые числа: регион 16, юрлица, ОКВЭД 49.41 → **177** новых. Регион 16, все ОКВЭД → **2660** новых.

**Ограничение по свежести, скажи о нём человеку сразу.** Реестр МСП обновляется **10-го числа каждого месяца**. Значит `is_new` и `dt_registry` дают дискретность **месяц, а не день**. Для еженедельного конвейера этого достаточно. Для ежедневного нужен повод 2.

### Повод 2. Дельта между срезами по ИНН

Самый сильный из доступных поводов, потому что он даёт **дневную дискретность** там, где у ФНС её нет.

Механика простая: `/продажи список` при каждом прогоне кладёт срез в таблицу **`snapshots`** (`dt_srez`, `inn`, `okved`, `employees`, `has_contracts`, `is_new`). Ты берёшь два последних среза и считаешь разницу.

Что ловит дельта:

| Изменение | Что это значит | Насколько сильный повод |
|---|---|---|
| **новый ИНН** в срезе | компания появилась в нише | сильный |
| **сменился `okved`** | компания перепрофилировалась | сильный, повод очень конкретный |
| **`employees` вырос** | компания растёт, объёмы растут | сильный: рост штата значит рост бюджета и потребностей (для перевозчика, например, это ещё и рост объёмов) |
| **`employees` упал** | сжимается | слабый, писать про это бестактно |
| **`has_contracts` стал 1** | компания зашла в госзаказ | сильный, у неё появились обязательства по срокам |
| **ИНН пропал из среза** | вышла из реестра МСП | не повод для письма, повод для отсева |

Дельта ловит не только новые регистрации, но и смену ОКВЭД, и возврат в реестр. Для лидогенерации это полезнее, чем чистые новые регистрации.

Важно: **серверного фильтра «зарегистрированы за последние N дней» у ФНС нет ни в одном из проверенных сервисов.** Ни в реестре МСП, ни в ЕГРЮЛ, ни в ГИР БО. Дата видна в выдаче, но фильтровать по ней приходится на клиенте. Поэтому дифф срезов это не костыль, а единственный рабочий способ.

Если срез в базе только один, дельту посчитать нельзя. Скажи об этом прямо: «первый срез записан, дельта появится со второго прогона». Не притворяйся, что нашёл изменения.

### Повод 3. Признак госконтрактов

Поле `has_contracts` из реестра МСП. Булев флаг «у компании есть госконтракты».

Это **бесплатная замена недоступному ЕИС**. Он не говорит, какой контракт и на сколько, но для повода этого хватает: компания, работающая с госзаказом, имеет закупочные процедуры, бюджет и жёсткие сроки перед заказчиком, а значит активнее закупает и подряжает по всем направлениям. Повод сильный в принципе, не только для одной ниши (для перевозчика, например, это прямое попадание: у такой компании точно есть что возить).

### Повод 4. Состояние сайта

Из фактов, собранных на обогащении: нет Яндекс.Метрики, копирайт двух-трёхлетней давности, нет адаптива, нет формы заявки, нет SSL, медленный ответ.

Живой пример из разведки: производственный сайт с копирайтом **2020** и без Метрики. Сайт не трогали шесть лет и никто не считает заявки.

Осторожно с этим поводом: он про сайт, а не про вашу нишу (для перевозчика, например, это не аргумент про перевозки). Использовать его как **повод написать** можно, как **аргумент в письме** обычно нельзя, получится нерелевантно. Решай по контексту своей ниши и предупреди человека.

### Повод 5. Рост выручки год к году (НОВОЕ)

Источник: **ГИР БО через функцию `get_bfo()` из `scripts/fns_bo.py`**. Она отдаёт бухотчётность компании сразу по нескольким годам одним дополнительным запросом: внутренний id организации (поле `id` в ответе поиска) уже есть после того, как компания найдена через `search_organizations()` или `iterate_all()`, второй запрос по этому id возвращает список записей по периодам с полями `period` и `gainSum`.

**Это самый быстрый способ получить сильный повод уже на первом прогоне**, потому что, в отличие от повода 2 (дельта срезов), второй прогон конвейера не нужен: рост считается по уже сданной отчётности за два года, которая лежит в ГИР БО прямо сейчас.

Механика:

1. Возьми `org_id` компании. **Внимание**: `company_row()` в `fns_bo.py` **не сохраняет `bo_id` в таблицу `companies`**, туда попадает только выручка за один период. Если id не сохранён, сделай точечный `search_organizations(inn=...)` (фильтр по ИНН на сервере точный, `totalElements=1`) и возьми `id` из ответа заново.
2. Вызови `get_bfo(org_id)`, отсортируй записи по `period` по убыванию и возьми два последних года.
3. Посчитай рост: `(gainSum_последний - gainSum_предыдущий) / gainSum_предыдущий`.
4. Порог значимости: рост примерно **20-30% год к году**.
5. Запиши `signal=rost_vyruchki`, `severity=high`, `source=gir-bo`, в `detail` конкретные суммы и годы, например «выручка выросла с 30 015 460 до 33 643 060 тыс. руб. за 2024→2025».

**Важно про `gainSum = null`.** Это значит «отчётность не показана» (не сдана или скрыта), а **не ноль выручки**. Такие компании в расчёт роста не бери: если `gainSum` пуст хотя бы в одном из двух периодов, пропусти компанию, не превращай `null` в 0. Клиентский фильтр `filter_by_revenue()` в `fns_bo.py` эту ловушку уже учитывает через `drop_unknown_revenue`, но при ручном сравнении двух периодов для дельты выручки следи за этим сам.

### Повод 6. Смена директора (НОВОЕ)

Источник: поле `g` из ЕГРЮЛ (`scripts/fns_egrul.py`, функции `search()` / `get_director()` / `parse_director()`), сравнение ФИО руководителя между двумя прогонами по одному ИНН.

Требует **минимум двух прогонов `fns_egrul.py` с разницей во времени**: это дельта, которая копится, как и повод 2, только медленнее. Первого прогона недостаточно, ты просто не с чем сравнивать.

**Практическое ограничение схемы хранения**: `save_directors()` в `fns_egrul.py` кладёт ФИО в `companies.director` через `db_upsert_company()`, а это **перезапись**, не история. Повторный прогон с `--refresh` затирает старое значение новым, и сравнить «было / стало» напрямую по `companies` уже не получится. Чтобы дельта работала, сохраняй значение `director` каждого прогона отдельно (например, тем же способом, каким повод 2 хранит `okved` и `employees` в `snapshots`) **до** следующего `--refresh`, и сравнивай именно с этим сохранённым значением.

Если ФИО изменилось, запиши `signal=smena_direktora`, `detail` вида «директор сменился: Иванов Иван Иванович → Петров Пётр Петрович», `source=delta_egrul`, `severity=medium`.

**ВАЖНОЕ ОГРАНИЧЕНИЕ.** Быстрый поиск ЕГРЮЛ, которым пользуется `fns_egrul.py`, отдаёт по ЮЛ только должность и ФИО руководителя (поле `g`) и название региона (поле `rn`). Он **не отдаёт полный адрес и не отдаёт список филиалов**, этих данных в схеме `normalize_row()` просто нет. Для адреса и филиалов нужна полная выписка ЕГРЮЛ, отдельный эндпоинт, которого в этом скрипте нет и который сюда не подключён. Поэтому повод «открылся новый филиал» **обещать нельзя**, строить его не из чего.

## Что требует российского IP, скажи это честно

**Обязательный блок. Не обещай человеку того, что у него не заработает, и не скрывай то, что заработает.**

| Сигнал | Источник | Статус |
|---|---|---|
| Вакансии по профилю вашей ниши (пример для демо-ниши: водителей и механиков) | `api.hh.ru/vacancies` | **403/401**, причина не всегда география, см. диагностику ниже |
| Карточка работодателя | `api.hh.ru/employers` | **403/401**, причина не всегда география, см. диагностику ниже |
| Справочники hh (регионы, отрасли, роли) | `api.hh.ru/areas`, `/dictionaries`, `/industries` | **200, работают отовсюду** (по последним замерам, тоже стоит перепроверять) |
| Кто выиграл госконтракт | `zakupki.gov.ru` | TLS-хендшейк не проходит, геоблок |
| Торги и имущество | `torgi.gov.ru`, `spending.gov.ru` | то же |
| Альтернатива по закупкам | `clearspending.ru` | proof-of-work защита Anubis, скриптом не берётся |

Блокировка hh раньше была поэндпоинтная и чисто по географии: справочники открыты всему миру, данные закрыты только по региону запроса. **С декабря 2025 это устарело.** Публичный анонимный доступ к `api.hh.ru` закрыт, и теперь для эндпоинтов с данными (вакансии, работодатели) может требоваться токен приложения **независимо от страны запроса** (источник: habr.com/ru/news/1069286). Старый диагноз «403 значит вы не в России» теперь может быть просто неверным.

**Диагностика по коду ответа hh, покажи её человеку:**

- **400 `bad_user_agent`** значит проблема в заголовке, это не изменилось. hh **банит User-Agent из собственной документации**. Строка `MyApp/1.0 (my-app-feedback@example.com)` из примера в доках даёт 400. Нужен уникальный UA с реальным контактом, например `LeadRadar/1.0 (dmitriy@comandos.ai)`
- **403 `forbidden`** или **401** значит **либо** вы не в России, **либо** hh требует токен приложения, которого у вас нет. **По одному коду ответа эти две причины не различить.**
- Единственный надёжный способ различить: **один пробный запрос с заведомо российского IP** перед тем, как доверять этому источнику вообще. Если он тоже отдаёт 403/401, дело не в географии, а в токене, и без регистрации приложения на dev.hh.ru вакансии не заработают ни у кого. Если пробный запрос с российского IP отдаёт 200, а у пользователя 403/401, тогда это география
- Не ставь пользователю диагноз «вы не в России» по одному коду 403 без этого пробного запроса, это теперь может быть ложью

Коды регионов hh **не совпадают с кодами ФНС**:

| Регион | код ФНС | area hh |
|---|---|---|
| Москва | 77 | **1** |
| Московская область | 50 | **2019** |
| Татарстан | 16 | **1624** |
| Казань | нет | **88** |

### Отдельно про вакансии: и повод, и признак отсева

Вакансии компании показывают, где у неё рост и где дефицит кадров, это универсальный сигнал, не привязанный к одной нише. Смотреть нужно на профиль вакансий под свою нишу, вот несколько примеров:

- вакансии водителей и механиков интересны перевозчику: сигнал, что у клиента есть свой автопарк или он его расширяет
- вакансии на производстве (технолог, оператор линии, кладовщик) интересны тому, кто поставляет сырьё или оборудование: сигнал роста объёмов производства
- вакансии в отделе продаж (менеджер по продажам, руководитель отдела продаж) интересны тому, кто продаёт CRM, скрипты продаж или обучение: сигнал, что отдел растёт и процесс под нагрузкой

Список ключевых слов для отсева берётся из `otsev.vakansii_stop_slova` в `config.json` (заполняется на шаге `/продажи портрет`) и ловит признак «закрывает потребность сам». Ключевые слова для повода в письме подбираются отдельно под свою нишу, они не обязаны совпадать с отсевом: для перевозчика оба списка про водителей и механиков и совпадают, а вот для того, кто продаёт CRM, отдел продаж это не отсев, а наоборот сильный повод, и такую компанию исключать по вакансиям нельзя.

**hh не умеет искать по ИНН.** Связка «компания из ЕГРЮЛ ↔ работодатель на hh» возможна только по названию, а это ненадёжный матчинг.

Поэтому вакансии по вашему профилю (в примере с перевозчиком: вакансии водителей) это **понижающий балл, а не жёсткий фильтр**. Формулируй результат именно так: «вероятно, закрывает потребность своими силами» (для демо-ниши: «вероятно, есть свой автопарк»), а не как утверждение. Жёсткий и точный признак только один, и он бесплатный: собственный профильный ОКВЭД компании в реестре (для демо-ниши это `49.41`), его применяет `/продажи отсев`.

## Ранг поводов по силе

Если у компании набралось несколько поводов, вот в каком порядке им доверять и что из них можно писать в текст письма как факт, а что нет:

| # | Повод | Почему такой ранг |
|---|---|---|
| 1 | **Дельта срезов по ИНН** (`snapshots`) | единственный источник с **дневной** детализацией: ловит новый ИНН, смену ОКВЭД, рост численности и появление госконтрактов день в день |
| 2 | **Госконтракты** (`has_contracts = 1`) | бюджет и жёсткие сроки перед заказчиком, компания активнее закупает и подряжает (для перевозчика, например, это прямое попадание) |
| 3 | **Рост выручки год к году** (НОВОЕ, повод 5) | самый быстрый способ получить сильный повод уже на первом прогоне, второй срез не нужен |
| 4 | **Новые в реестре** (`is_new = 1`) | месячная детализация, реестр обновляется 10-го числа |
| 5 | **Смена директора** (НОВОЕ, повод 6) | требует минимум двух прогонов ЕГРЮЛ с разницей во времени, копится медленнее дельты снапшотов |
| 6 | **Вакансии hh** | понижающий балл, не факт: hh не ищет по ИНН, матчинг только по названию |
| 7 | **Протухший сайт** | только приоритизация очереди, кому писать в первую очередь. **Не аргумент письма** |

Практический вывод: поводы 1-5 можно ставить в письмо как факт с числами. Повод про вакансии (ранг 6) формулируй осторожно («вероятно, закрывает потребность своими силами», для демо-ниши: «вероятно, есть свой автопарк»), а не как утверждение. Повод про сайт (ранг 7) используй только чтобы решить очерёдность, в тексте письма про вашу нишу он обычно нерелевантен.

## Пошаговый алгоритм

1. Прочитай `companies` и `snapshots` из `data/leads.db`.
2. Посчитай **дельту** между двумя последними срезами по `inn`. Если срез один, честно скажи об этом.
3. Отбери компании с `is_new = 1`.
4. Отбери компании с `has_contracts = 1`, отдельно выдели тех, у кого этот флаг **появился** в последней дельте.
5. Посчитай **рост выручки**: для компаний с уже известным `id` в ГИР БО (или после точечного `search_organizations(inn=...)`) вызови `get_bfo(org_id)`, сравни два последних периода, отбери рост от 20-30% и выше. Пропусти компании, где `gainSum` хотя бы одного периода `null`.
6. Сравни **директора**: если для компании сохранена история `director` из предыдущего прогона `fns_egrul.py`, сверь её с текущей. Если истории ещё нет, честно скажи, что дельта по директору появится со второго прогона, так же как для повода 2.
7. Подними из `enrichment` (колонка `facts_json`) технические признаки протухшего сайта.
8. Проверь доступность российских источников **одним пробным запросом**, а не пачкой:
   ```bash
   curl -s -o /dev/null -w '%{http_code}' 'https://api.hh.ru/vacancies?text=водитель&area=1624&per_page=1' \
     -H 'User-Agent: LeadRadar/1.0 (dmitriy@comandos.ai)'
   ```
   `text=водитель` здесь пример поискового слова для демо-ниши, подставь ключевое слово своей ниши. 200 значит источник доступен, работаем с вакансиями. 403 или 401 значит источник недоступен: либо не тот регион, либо нужен токен приложения, по коду это не различить (см. диагностику hh выше). Отключаем блок вакансий и **говорим об этом человеку прямо**, не выдавая догадку за диагноз.
9. Разложи поводы по компаниям. У одной компании может быть несколько, отсортируй по **рангу силы** (см. раздел выше).
10. Запиши поводы в таблицу **`signals`**, **по одной строке на один повод**:

| Колонка | Что кладёшь |
|---|---|
| `inn` | ключ компании |
| `name` | название, чтобы отчёт читался без джойна |
| `signal` | тип повода коротко: `novaya_v_reestre`, `smena_okved`, `rost_chislennosti`, `poyavilis_goskontrakty`, `rost_vyruchki`, `smena_direktora`, `protuhshiy_sayt` |
| `detail` | конкретика с числами: «численность выросла с 34 до 61 за месяц» |
| `severity` | сила повода: `high`, `medium`, `low` |
| `source` | откуда: `rmsp`, `delta`, `gir-bo`, `delta_egrul`, `site` |
| `checked_at` | когда посчитано |

У одной компании может быть несколько строк, это нормально и правильно: отчёт группирует их сам.

11. Собери отчёт.

## Отчёт

**HTML руками не пиши**, его собирает `scripts/report.py` из таблицы `signals`.

```bash
PRODAZHI="$HOME/.claude/tools/prodazhi"; [ -d "$PRODAZHI/scripts" ] || PRODAZHI="$(pwd)"
python3 "$PRODAZHI/scripts/report.py" --db data/leads.db --out out --only signaly
open out/signaly.html
```

Это **отчёт шага 4 из 5**. Генератор сгруппирует поводы по типу и отсортирует по `severity`, поэтому качество отчёта держится на поле `detail`: пиши туда числа и даты, а не общие формулировки.

**Блок про недоступное с этого IP покажи сам, в чате**, отдельно от отчёта: какие источники не проверялись и почему это география, а не поломка. Этот блок обязателен, даже если пуст.

## Какие скрипты запускает

| Скрипт | Роль |
|---|---|
| `scripts/fns_rmsp.py` | новый срез в `snapshots`, если сегодняшнего ещё нет |
| `scripts/fns_bo.py` (`get_bfo()`) | живой запрос по `org_id` для повода 5, рост выручки. В основной поток обогащения не подключена, вызывай отдельно |
| `scripts/fns_egrul.py` | ФИО директора для повода 6. Само сравнение делается по сохранённой истории, не по одному прогону |

Дельта и разбор поводов делаются запросами к `data/leads.db`, отдельный скрипт для этого не нужен. Отчёт собирает `scripts/report.py`.

Если в репозитории появится `scripts/hh_vacancies.py`, проверь его через `grep -n 'argparse' scripts/hh_vacancies.py`, а **не через `--help`**, и запускай только при подтверждённом российском IP.

## Возможные ошибки и что делать

| Симптом | Причина | Что делать |
|---|---|---|
| Дельта пустая | в базе один срез | так и скажи: дельта появится со второго прогона. Не выдумывай изменения |
| Дельта показывает сотни новых | сравниваются срезы разных ниш или разных регионов | сравнивай срезы с одинаковыми параметрами выборки, иначе разница бессмысленна |
| `is_new` не меняется неделями | реестр обновляется 10-го числа | это норма, не баг. Дневную дискретность даёт только дельта срезов |
| hh отдаёт 403 или 401 | либо зарубежный IP, либо (с декабря 2025) нужен токен приложения, по коду не различить | сделай пробный запрос с заведомо российского IP. Если он тоже 403/401, дело не в географии. Блок вакансий отключить и сказать человеку честно, какая причина, а если не удалось выяснить, так и сказать |
| hh отдаёт 400 `bad_user_agent` | взят UA из документации hh, он в чёрном списке | поставь уникальный UA с реальным контактом |
| Вакансии нашлись не у той компании | hh не ищет по ИНН, матчинг по названию | понижающий балл, а не факт. В письмо это утверждение не ставить |
| `zakupki.gov.ru` висит и отваливается по таймауту | геоблок на уровне TLS, TCP при этом открывается | не лечится ретраями. Используй `has_contracts` из реестра МСП |
| Хочется взять закупки через clearspending | там proof-of-work Anubis | скриптом не берётся, нужен браузер. Не трать на это время |
| У всех компаний одинаковый повод | взят только `is_new` | добавь дельту, `has_contracts` и рост выручки, иначе письма будут выглядеть одинаково |
| Рост выручки посчитан от `null` как от нуля | `gainSum = null` значит «отчётность не показана», а не 0 | пропускай компанию, если `gainSum` пуст хотя бы в одном из двух периодов |
| Не могу вызвать `get_bfo()`, нет `org_id` | `company_row()` в `fns_bo.py` не сохраняет `bo_id` в `companies` | сделай точечный `search_organizations(inn=...)` и возьми `id` из ответа заново |
| Смена директора не считается, хотя ФИО правда сменилось | `companies.director` перезаписывается каждым прогоном `fns_egrul.py` с `--refresh`, истории нет | сохраняй значение `director` перед следующим `--refresh` отдельно и сравнивай именно с ним, как в поводе 2 |
