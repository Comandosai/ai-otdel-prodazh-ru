# Продажи: бесплатный отсев

## Что делает

Выбрасывает из выборки всё, что можно выбросить **бесплатно и без единого запроса к сайтам компаний**.

Это самый важный шаг по экономике всего конвейера. Обогащение стоит времени: один сайт это несколько секунд, один запрос в ЕГРЮЛ около **2 секунд**. Если из 5084 компаний реально подходят 300, то отсев до обогащения экономит примерно четыре с половиной тысячи запросов. Отсев после обогащения не экономит ничего.

Правило: **сначала режем по тому, что уже лежит в базе, потом добираем недостающее из ГИР БО, и только выжившие идут в обогащение.**

## Когда вызывать

- после `/продажи список`, всегда
- когда человек хочет ужесточить или ослабить фильтр без пересбора выборки
- когда после обогащения выяснилось, что в работу попало много мусора

## Пошаговый алгоритм

### Шаг 0. Вход и модель отсева

Прочитай `config.json` (блоки `vilki` и `otsev`) и таблицу `companies` из `data/leads.db`. Запомни стартовое число компаний, оно понадобится для воронки.

Конфиг в конвейере один, отдельного `config/icp.json` нет. Путь вычисляй, рабочая папка человека может быть любой:

```bash
PRODAZHI="$HOME/.claude/tools/prodazhi"; [ -d "$PRODAZHI/scripts" ] || PRODAZHI="$(pwd)"
cat "$PRODAZHI/config.json"
```

**Ничего не удаляй из `companies`.** Отсев это отдельная таблица, а не правка исходных данных. Пиши отсеянных в таблицу **`otsev`**:

| Колонка | Что кладёшь |
|---|---|
| `inn` | ключ компании |
| `name` | название, чтобы отчёт читался без джойна |
| `reason` | причина **человеческим языком** с числом: «численность 4 человека, вилка от 20» |
| `rule` | короткий машинный код правила: `svoy_okved`, `chislennost`, `vyruchka`, `status`, `massovyy_adres` |
| `dropped_at` | когда отсеяли |

**Одна компания попадает в `otsev` один раз**, по первому сработавшему правилу. Иначе воронка перестанет сходиться.

Выжившие после этого определяются запросом, отдельной колонки-флага **не заводи**:

```sql
SELECT * FROM companies
WHERE inn NOT IN (SELECT inn FROM otsev);
```

Так человек в любой момент видит и полный исходный список, и причину по каждому вычеркнутому, и может вернуть компанию, просто удалив строку из `otsev`.

**Отложенные**, то есть те, по кому не хватило данных для решения, тоже кладутся в `otsev`, но с префиксом в `rule`: `otlozheno_vyruchka`, `otlozheno_chislennost`. Тогда они видны отдельной группой и не теряются молча.

### Шаг 1. Бесплатные фильтры, данные уже в базе

Эти четыре не требуют ни одного сетевого запроса.

**1.1 Численность.** Колонка `employees` таблицы `companies`, пришла из реестра МСП. Режь по `vilki.chislennost_ot` и `vilki.chislennost_do`. Компании с пустой численностью **не выбрасывай в общую кучу**, клади в `otsev` с правилом `otlozheno_chislennost` и решай с человеком: пустое поле это не ноль сотрудников.

**1.2 Собственный профильный ОКВЭД.** Главный приём: исключить тех, кто закрывает вашу потребность сам. Если в `okved` компании стоит код из `otsev.isklyuchit_okved`, она попадает под ваш признак отсева. **Пример для демо-ниши**: код `49.41` значит, что у компании **свой автопарк**, значит перевозчику она не клиент. У вас в `isklyuchit_okved` будет свой код под свой признак, механика та же.

Важное ограничение, скажи о нём честно: в реестре МСП лежит **только основной ОКВЭД**, поле `okved1`. Дополнительные виды деятельности туда не попадают. Значит компания с основным ОКВЭД «производство хлеба» и дополнительным `49.41` этим фильтром **не поймается**. Это не жёсткий фильтр, а дешёвый первый проход, который ловит очевидные случаи.

**1.3 Возраст.** Считай от `dt_registry`. Оговорка: это дата включения в **реестр МСП**, а не дата регистрации компании в ЕГРЮЛ. Они часто не совпадают. Точная дата регистрации приходит только на шаге обогащения, из ЕГРЮЛ, поле `r`. Поэтому на этом шаге возраст режь **мягко**, только явные случаи, а точную отсечку делай после обогащения.

**1.4 Категория МСП.** Колонка `category`: 1 микро, 2 малое, 3 среднее. Фильтруй локально, серверный фильтр реестра в замерах игнорировался.

### Шаг 2. Выручка из ГИР БО

Выручки в реестре МСП нет. Её нужно добрать из `bo.nalog.gov.ru`. Капчи там нет: 25 запросов подряд за 23.7 секунды прошли без единой ошибки.

Запрос:

```
GET https://bo.nalog.gov.ru/advanced-search/organizations
    ?okved=10.71&address=ТАТАРСТАН
    &period=2025&page=0&size=2000
```

Заголовки: `Accept: application/json`, `Referer: https://bo.nalog.gov.ru/`.

**Параметров `gainSumFrom` и `gainSumTo` в запросе нет намеренно: серверного фильтра по выручке у ГИР БО не существует.** Проверено живыми запросами 13.08.2026: сервер принимает оба параметра без ошибки и молча их игнорирует, выдача не меняется ни при каком диапазоне, включая заведомо абсурдные. Ведут себя ровно как параметр, которого у API нет. Не добавляй их и не объясняй ими сужение выдачи.

Выручку бери из поля **`bfo.gainSum`** каждой записи и **фильтруй по вилке у себя в коде**. Единица `gainSum` это тысячи рублей, и в `config.json` поля `vilki.vyruchka_tys_rub_ot` и `vilki.vyruchka_tys_rub_do` уже записаны в тысячах: бери как есть, ничего не домножай.

**`gainSum` бывает `0` и бывает `null`.** В проверенном срезе из 119 записей: 95 с числом, 8 нулей, 24 `null`. **`null` означает «отчётность за этот период не показана», а не «выручка ноль»**, и складывать их в одну корзину нельзя. Реши явно и скажи человеку, куда девать записи без выручки: в отдельную очередь или в отсев.

Четыре обязательных правила работы с этим эндпоинтом:

1. **`size` максимум 2000.** `size=5000` сервер молча урезает до 2000.
2. **Глубина жёстко ограничена: `size * page < 10000`.** На `size=2000&page=5` приходит **HTTP 500**. Оптимальный режим: `size=2000`, страницы 0-4, то есть 10 000 записей за 5 запросов. Если ниша шире, дроби запрос **по регионам, по ОКВЭД и по отчётным периодам**. По диапазонам выручки резать нельзя: `gainSumFrom` / `gainSumTo` не фильтруют.
3. **`address` это подстрочный поиск по всему адресу, включая улицу.** Запрос `address=ТАТАРСТАН` подтянет компанию из Набережных Челнов с улицы Татарстан. Используй `address` только как грубое сужение, а **регион чисти на клиенте по полю `region`**.
4. **В ответе совпадения обёрнуты в `<strong>...</strong>`.** Вычищай теги перед записью в базу, иначе они уедут в письмо.

Сопоставление с базой **только по ИНН**. По названию не сопоставляй никогда, названия не уникальны.

Выручку клади в колонку **`revenue`** таблицы `companies`, туда же `status` (`ACTIVE` / `INACTIVE`), `status_date` и `address`. Единица в `revenue` та же, **тысячи рублей**, не пересчитывай.

**Компании, которой нет в ГИР БО, не выбрасывай по причине «нет выручки».** ГИР БО знает только тех, кто сдавал бухотчётность, это другая генеральная совокупность. Живые числа по ОКВЭД 10.71 в Татарстане: реестр МСП знает **290** организаций, ГИР БО **159**. Расхождение нормально. Клади их в `otsev` с правилом `otlozheno_vyruchka` и решай с человеком.

**Альтернатива для больших объёмов.** Открытый набор `revexp` (`https://file.nalog.ru/opendata/7707329152-revexp/`, 99.5 МБ, XML по схеме рядом) содержит доходы и расходы **по ИНН для всех организаций РФ**. Поля `ИННЮЛ`, `СумДоход`, `СумРасход`. Если выборка больше нескольких тысяч, один раз скачать набор дешевле, чем ходить в ГИР БО постранично. Оговорка честная: разведка разобрала этот набор **по XSD и по заголовку архива через Range-запрос**, целиком его не качали и не распаковывали. Перед тем как строить на нём отсев, проверь на десятке ИНН, что значения бьются с ГИР БО.

### Шаг 3. Статус

Выбрасывай `INACTIVE` из ГИР БО и `is_active = 0` из реестра МСП, если в конфиге стоит `tolko_deystvuyushchie`. Заполненная `dt_registry_out` означает исключение из реестра МСП, это тоже повод присмотреться, но не всегда повод выбросить: компания могла просто перерасти категорию МСП.

### Шаг 4. Массовые адреса и массовые руководители

Открытые данные ФНС, скачиваются прямыми ссылками без ключа:

| Набор | Что даёт |
|---|---|
| `masaddress` | адреса массовой регистрации. Сильный признак пустышки |
| `massleaders` | физлица, руководящие несколькими юрлицами. Признак номинала |
| `registerdisqualified` | реестр дисквалифицированных лиц |

Каталог: `https://www.nalog.gov.ru/opendata/`.

**Честная пометка: структура этих трёх наборов разведкой не проверялась.** Подтверждено только, что они существуют в каталоге и заявлены как CSV. Прежде чем резать по ним, скачай, посмотри первые строки, убедись в кодировке и в том, какое поле является ключом. Если структура не та, что ожидалась, **пропусти этот фильтр и скажи об этом человеку**, а не выдумывай результат.

Фильтр по массовому адресу требует адреса, а он появляется только после шага 2. Фильтр по массовому руководителю требует ФИО, а оно появляется только на обогащении. Значит: **массовый адрес режь здесь, массового руководителя проверяй уже после обогащения** и помечай результат обратно в эту же колонку.

### Шаг 5. Воронка с числами

Собери таблицу вида «было, отсеяно, осталось» по каждому фильтру **в том порядке, в котором фильтры применялись**. Порядок важен: одна компания может подходить под три причины, и засчитать её надо один раз, по первой сработавшей.

```
Собрано из реестра МСП                        5084
  минус свой ОКВЭД 49.41                      -3120   →  1964
  минус численность вне вилки 20..250          -890   →  1074
  минус статус не действующий                   -47   →  1027
  минус выручка вне вилки 50 млн..2 млрд       -603   →   424
  минус массовый адрес                          -31   →   393
  ────────────────────────────────────────────────────────────
  Идут в обогащение                                       393
  Отложены, данных не хватило                             118
```

Строка «отложены» обязательна. Туда попадают те, у кого не нашлось выручки или численности. Это **не отсеянные**, это те, по кому решение не принято, и человек должен видеть их отдельно.

### Шаг 6. Отчёт

**HTML руками не пиши**, его собирает `scripts/report.py` из таблицы `otsev`.

```bash
PRODAZHI="$HOME/.claude/tools/prodazhi"; [ -d "$PRODAZHI/scripts" ] || PRODAZHI="$(pwd)"
python3 "$PRODAZHI/scripts/report.py" --db data/leads.db --out out --only otsev
open out/otsev.html
```

Это **отчёт шага 2 из 5**. Генератор сам сгруппирует отсеянных по `rule` и покажет причины из `reason`, поэтому качество отчёта напрямую зависит от того, насколько внятно ты заполнил `reason`. Пиши туда числа, а не общие слова: «численность 4 человека, вилка от 20» читается, «не подходит по размеру» не читается.

Если отчёт показывает плашку «таблица не создана», значит в `otsev` ничего не записано.

## Какие скрипты запускает

| Скрипт | Роль |
|---|---|
| `scripts/fns_bo.py` | добор выручки, адреса и статуса из ГИР БО. Внутри уже есть защита от превышения глубины 10 000 и клиентская чистка региона |

Проверяй интерфейс через `grep -n 'argparse\|add_argument' scripts/fns_bo.py`, а **не через `--help`**: демо-режимный скрипт на `--help` не покажет справку, а запустится целиком и пойдёт в сеть. Сам отсев делается запросами к `data/leads.db`, отдельный скрипт для этого не нужен.

## Что показывает человеку

- воронку с числами по каждому фильтру
- **какой фильтр съел больше всего** и предложение обсудить его порог
- примеры отсеянных, чтобы решение можно было проверить
- отдельно отложенных, по кому не хватило данных
- честную оговорку про основной ОКВЭД: фильтр по вашему коду отсева (для демо-ниши это «свой автопарк» у кода 49.41) ловит только тех, у кого этот код стоит **основным** видом деятельности
- ссылку на `out/otsev.html`
- следующий шаг: `/продажи обогащение`

## Возможные ошибки и что делать

| Симптом | Причина | Что делать |
|---|---|---|
| HTTP 500 от ГИР БО | `size * page` дошло до **10000** | предел глубины ровно 10 000 записей. Дроби по регионам, ОКВЭД и отчётным периодам. По выручке дробить нельзя, `gainSumFrom` / `gainSumTo` не фильтруют |
| `size=5000` вернул 2000 | сервер молча урезает | максимум `size` = 2000 |
| В выборке компании из другого региона | `address` ищет по всему адресу, включая улицу | чисти регион **на клиенте** по полю `region` |
| В названиях в базе торчит `<strong>` | подсветка совпадений в ответе ГИР БО | вычищай теги при записи, проверь уже загруженные строки |
| Выручка отличается в 1000 раз | перепутаны рубли и тысячи | `gainSum` и вилка в конфиге **в тысячах рублей** |
| Выручка не нашлась у трети компаний | ГИР БО знает только сдававших отчётность | это норма. Молча не выбрасывай и молча не оставляй: правило `otlozheno_vyruchka` и вопрос человеку |
| Отсеялось больше 95% выборки | пороги слишком узкие либо перепутана единица выручки | покажи воронку, назови самый прожорливый фильтр, предложи ослабить, не продолжай молча |
| Не отсеялось почти ничего | фильтры не применились, скорее всего пустые поля | проверь, что `employees` и `revenue` реально заполнены, а не `NULL` у всех |
| CSV массовых адресов не парсится | структура набора разведкой не проверялась | **пропусти фильтр**, скажи об этом человеку прямо. Не имитируй результат |
| Хочется добрать данные из pb.nalog.ru | там есть готовый `bourl` | не ходи туда пачкой. Капча по IP, держится больше 30 минут |
